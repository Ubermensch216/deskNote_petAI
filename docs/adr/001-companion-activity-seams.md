# ADR 001: 컴패니언 활동 접점은 메모 기능과 분리한다

상태: Accepted  
결정일: 2026-08-31

## 배경

컴패니언은 기록·회상·해결 행동을 관찰해야 하지만, 메모 저장과 검색이 게임 규칙을 알아서는 안 된다.
또한 자동 저장 한 번, 창 열기 한 번을 곧바로 성장으로 취급하면 입력 중 반복 저장과 같은 메모 재열기로
보상이 증식한다.

## 결정

메모 계층은 해석되지 않은 typed fact만 제공한다.

- `NoteSaveResult`: 저장 전후 본문, 실제 변경 여부, 성공 시각
- `NoteOpenContext`: 라이브러리·검색·관련 메모·AI 근거·알림 등 진입점
- `NoteOpened`: 요청이 아니라 메모가 실제로 포커스된 뒤의 사실

컴패니언 계층은 이후 이 사실에 체류 시간, 후속 행동, 일일 상한, 멱등 키를 결합해 성장 이벤트를
판정한다. 컴패니언 기록 실패는 메모 저장 실패로 전파하지 않는다.

## 체크리스트 완료 키

현재 체크리스트는 Markdown 본문이 원본이고 `checklist_items`는 저장할 때 다시 만드는 투영이다. 따라서
투영 행의 임시 ID를 영구 보상 키로 사용하지 않는다.

MVP에서는 다음 값을 정규화해 completion key를 만든다.

```text
SHA-256(note_id | normalized_text | first_seen_local_date)
```

- `normalized_text`: 앞뒤 공백 제거, 연속 공백 축소, 대소문자 정규화
- 같은 노트 안에 같은 문구가 여러 개면 ordinal을 추가한다.
- 문구가 바뀌면 새 업무로 취급하되 하루 해결 상한이 스팸을 제한한다.
- 완료→미완료→재완료는 같은 key이므로 한 번만 보상한다.

향후 체크리스트에 본문 밖 안정 ID를 삽입하는 방식은 Markdown 이식성을 해치므로 MVP에서 채택하지 않는다.

## 결과

- 저장·검색·알림은 컴패니언 없이 계속 동작한다.
- 게임 규칙 버전을 바꿔도 메모 API를 바꿀 필요가 없다.
- 회상 판정과 보상 중복 방지를 순수 도메인 테스트로 검증할 수 있다.
- 텍스트가 완전히 같은 별도 업무가 같은 날 같은 노트에 존재하면 ordinal 의존성이 생기는 한계가 있다.
