# 로컬 AI

AI는 [Ollama](https://ollama.com)를 통해 로컬에서만 돈다. `ILocalAiService` 뒤의 구현이
`src/DeskNote.Ai`의 `OllamaAiService`이고, 인터페이스가 요구하는 "모델은 별도 프로세스에서"
격리는 Ollama 자체가 별도 프로세스라 그대로 충족된다. 데몬이 죽으면 HTTP 호출이 실패해 AI가
"사용 불가"로 내려갈 뿐, 메모 창은 아무 영향도 받지 않는다.

```bash
ollama pull gemma4:e2b
```

```bash
ollama pull bge-m3
```

설치·서버 기동·모델 내려받기·연결 확인을 한 번에 하려면 `scripts/install-ai.bat` 을 실행한다
(진단만 하려면 `-CheckOnly`). 단계별 설명은 [README](../README.md#ai-설치하고-연결하기)에 있다.

| 설정 키 | 기본값 | 뜻 |
|---|---|---|
| `ai.enabled` | (없음 = 켬) | `false` 면 소켓조차 열지 않는다 |
| `ai.endpoint` | `http://localhost:11434` | 로컬 추론 서버 주소 |
| `ai.model` | `gemma4:e2b` | 텍스트 동작에 쓰는 모델 |
| `ai.embeddingModel` | `bge-m3:latest` | 검색 임베딩용 모델 |
| `ai.keepAliveMinutes` | `15` | 모델을 메모리에 유지하는 시간 (0~60분, `0` 이면 즉시 내림) |

값이 깨져 있으면 기본값으로 되돌아간다. AI 설정을 잘못 써서 앱이 못 뜨는 일은 없다.

가용성 확인(`/api/tags`)은 메모가 화면에 뜬 뒤 백그라운드에서 시작하고 1분마다 다시 확인한다.
가중치는 이 경로에서 절대 로드하지 않는다 (보고서 p14: "앱 시작 = 모델 시작" 금지).

## AI 기능은 한국어 전용이다

모델에게 보내는 지시문 — 정책, 동작별 지시, 말투, 요일 이름까지 — 은 전부 한국어로 쓰여 있고
`src/DeskNote.Ai/AiPrompts.cs` 한 곳에 모여 있다. 번역 대상이 아니라 **의도된 제약**이다.

앱 UI 자체는 한국어와 영어를 모두 지원한다(`Strings/*/Resources.resw`). 하지만 UI를 영어로 두어도
AI는 한국어 지시문으로 동작하며, 답변 언어 한 줄만 요청 언어를 따라간다. 작은 모델에게 "한국어로
지시받고 영어로 답하라"는 신뢰하기 어려운 부탁이므로, **영어 UI + AI 조합은 지원 범위 밖이다.**

그래서 `LocalizationGuardTests` 의 하드코딩 문자열 검사는 `src/` 전체를 훑되 `DeskNote.Ai` 만
명시적으로 제외한다. 프롬프트는 UI가 아니고 사용자가 볼 일도 없으며, 리소스 시스템에 넣으면
프롬프트와 그 규칙을 한 덩어리로 읽는다는 유일한 장점을 잃는다.

영어 AI를 실제로 만들 일이 생기면 시작점은 그 예외 항목이다. 지우고 테스트를 돌리면 번역해야 할
프롬프트 목록이 그대로 나온다. 번역량보다 **동작 9종의 출력 품질을 모델로 다시 확인하는 일**이
비용의 대부분이다.

## 본문은 데이터이지 지시가 아니다

본문·선택 영역·제목은 언제나 시스템 프롬프트가 아니라 사용자 메시지의
`<UNTRUSTED_NOTE_CONTEXT>` 블록 안에 들어가고, 본문이 그 구분자를 흉내 내면 지워진다 (보고서 p16).
할 일 추출과 태그 제안은 JSON 스키마로 디코딩을 강제한 뒤 한 번 더 검증한다 — 읽을 수 없는 날짜는
추측하지 않고 버린다 (보고서 p11).

## 이 하드웨어에서 걸리는 시간

i7 / 16GB CPU 추론에서 gemma4:e2b 기준 요약 약 25초, 할 일 추출 약 45초가 걸린다. 모델이 메모리에
올라가 있지 않은 첫 호출은 7.2GB를 읽어 들이느라 60초에 가깝다.

**출력이 짧다고 빨라지지는 않는다.** 알림 파싱은 타임스탬프 하나만 돌려주는데도 모델이 올라가 있는
상태에서 40~80초가 걸린다 — 이 하드웨어에서 시간을 먹는 것은 토큰 생성이 아니라 프롬프트 처리와
모델 스케줄링이다. 그래서 "짧은 생성은 대화형으로 써도 된다" 는 가정은 이 CPU에서 성립하지
않으며, 명령 팔레트가 모델을 절대 기다리지 않는 이유가 그것이다. 모든 동작은 취소 가능하고,
결과는 적용 전까지 메모에 쓰이지 않는다.

그 60초를 두 번 내지 않기 위해 두 가지를 한다. 모든 요청에 `keep_alive` 를 실어 보내
(`ai.keepAliveMinutes`, 기본 15분) Ollama 기본값인 5분 유휴 언로드를 늘리고, **`✨ AI` 메뉴가
열리는 순간** 빈 메시지 요청으로 모델을 미리 올린다. 사용자가 타일을 고르는 몇 초가 로딩과
겹치는 셈이다. 예열은 순수한 최적화라 실패해도 아무것도 보고하지 않는다 — 데몬이 죽어 있으면
타일은 이미 비활성이고, 살아나면 다음 프로브가 알아챈다. `keep_alive` 는 요청마다 보낸다:
Ollama 는 마지막으로 받은 값을 적용하므로 한 번이라도 빠뜨리면 기본값으로 돌아간다.

## 다듬기와 재작성

노트 위쪽의 **`✨ AI`** 버튼에서 고른다. 텍스트를 선택해 두면 그 부분만, 선택이 없으면
메모 전체가 대상이다.

| 타일 | 동작 |
|---|---|
| 요약 / 정리 | 핵심만 남기기 / 제목·목록·체크박스로 구조화 |
| 간결 · 격식 · 친근 · 보고서 | 같은 내용을 그 어조로 다시 쓰기 |

긴 메모(6,000자 초과)는 **나누어 요약한 뒤 합친다**. 한 번에 넣으면 실패하지 않고 앞부분만 요약한
채 나머지를 조용히 버리는데, 회의록에서 그것은 최악의 결과다. 3,000자 구간마다 한 번씩 부르고 마지막에
합치므로 12,000자 메모는 다섯 번 부른다 — CPU에서 몇 분이다. 그 값은 메모 끝까지 다루는 답이고,
그만큼 긴 메모만 낸다.

누르면 미리보기 창이 **먼저** 뜨고 (CPU에서 수십 초가 걸리므로 기다리는 중임을 보여준다),
끝나면 원본과 제안을 나란히 보여준다. **적용**을 눌러야 본문이 바뀌고, 그 편집은 일반 편집과
똑같이 `Ctrl+Z` 로 되돌아가며 리비전으로 남는다. 창을 닫으면 추론이 취소된다.

모델이 답하는 동안 메모를 고쳤다면, 적용 대상 구간이 더 이상 같지 않으므로 적용을 거부하고
그 사실을 알린다 — 사용자가 방금 쓴 문장을 오래된 제안으로 덮어쓰지 않는다.

### 선택한 부분만

본문에서 텍스트를 선택하면 서식 막대 끝에 `요약` 과 `간결` 이 나타난다. 둘 다 선택 영역만 대상으로
하며, AI 메뉴로 가는 것과 같은 동작이되 세 번 누르지 않아도 되고 메뉴가 손보려는 바로 그 텍스트를
가리지도 않는다. 선택이 없거나 모델이 없으면 `Collapsed` 라 자리를 차지하지 않는다 — 서식 막대는
이미 보통 크기 노트가 가진 298pt 중 219pt를 쓰고 있어서, 이 둘은 남은 자리에 들어가야 한다.

### 결과가 메모에 들어가는 모양

메모는 글꼴 하나짜리 평범한 텍스트 상자다. `**중요**` 를 굵게 그려 주는 것이 없으므로 그 별표
네 개는 서식이 아니라 눈이 건너뛰어야 할 문장 부호다. 그래서 모델의 답은 사용자에게 보이기 전에
**메모가 실제로 그릴 수 있는 것만 남기고** 정리된다 (`AiTextCleanup`).

| | |
|---|---|
| 남는 것 | `- ` 목록 · `- [ ] ` 체크박스 · `1. ` 번호 · `#태그` · URL |
| 없어지는 것 | `**굵게**` · `*기울임*` · 인라인 코드 · `~~취소선~~` · `# 제목` · 표 · 코드 블록 · 구분선 |

남기는 쪽은 취향이 아니라 기능이다. 체크박스는 눌러서 토글되고, 목록은 Enter로 이어지고,
해시태그는 저장할 때 `tags` 테이블로 투영된다 — 이것들을 지우면 메모를 정돈하는 게 아니라
망가뜨린다. 소제목은 기호를 뗀 한 줄로 남는데, 크기가 하나뿐인 화면에서 `##` 는 "여기서 글자가
커졌어야 했다" 는 말밖에 하지 못하기 때문이다.

정리는 **미리보기에 보여 주기 전에** 돌린다. 사용자가 승인한 문장과 메모에 들어간 문장이 다르면
미리보기가 존재할 이유가 없다. 할 일 추출의 제목도 같은 처리를 거치므로, 확인 목록에 보이는 줄이
곧 메모에 붙는 줄이다.

프롬프트도 같이 고쳤다. 모델에게 평문으로 답하라고 먼저 부탁하고, 그래도 남는 것을 위 정리가
받아낸다 — 작은 로컬 모델이 가장 먼저 잊는 것이 서식 지시이고, 그 사실을 메모에서 확인할 수는
없기 때문이다. 짝이 맞는 표시만 걷어내므로 `2 * 3` 이나 `note_repository` 는 그대로 살아남는다.

AI가 준비되지 않았으면 타일이 비활성화되고 메뉴 맨 아래에 이유가 표시된다 (모델 없음 / 서버
미실행 / 꺼짐). 준비됐으면 모델 이름과 실행 위치(CPU·GPU)가 같은 자리에 표시된다.

## 할 일 추출과 태그 제안

AI 메뉴 **뽑아내기** 의 `할 일` · `태그` 는 본문을 고쳐 쓰는 대신 **목록을 제안**한다. 모델은 세 개는
맞히고 하나는 틀릴 수 있으므로, 항목마다 체크박스가 따로 붙는다. 기본은 전부 선택돼 있고, 적용은
선택한 것만 반영한다.

- 할 일 → 본문 끝에 `- [ ] 제목` 으로 붙는다. 마감이 있으면 그 시각에 이 메모의 알림이 걸린다.
  마감·담당·중요도는 확인 목록에서 보여 주되 본문 줄에는 넣지 않는다 — 본문은 사용자의 문장이다.
- 태그 → 본문 끝에 `#태그` 로 붙는다. 이미 달려 있는 태그는 제안 목록에서 빠진다.

**태그는 모델보다 이웃에게 먼저 묻는다.** 같은 주제를 다루는 메모 셋이 이미 달고 있는 태그가 대개
가장 좋은 후보이고, 그것을 알아내는 데는 벡터 읽기 한 번이면 된다 — 모델이 하나를 지어내는 데 드는
45초 대신. 이웃이 없을 때(새 주제이거나 아직 색인되지 않은 라이브러리)만 모델을 부른다. 실측으로
이웃에서 나오는 경우 **0.0초** 다.

이웃에서 온 태그에는 확신도를 붙이지 않는다. 다른 메모에 대한 사실이지 추측이 아니므로, 지어낸
100% 대신 `비슷한 메모에서` 라고 출처를 적는다. 여러 이웃이 함께 단 태그일수록 위로 온다 — 셋이
동의한 태그는 주제를 가리키고, 한 번만 나온 태그는 그 메모에서 있었던 일일 수 있다.

뽑아낼 것이 없으면 빈 목록 대신 "제안할 것이 없습니다" 라고 말한다. 마감이 적히지 않은 할 일에
날짜를 지어내지 않는 것과 같은 이유다.

## 제목

메모의 이름은 본문 첫 줄이다. 그래서 `- [ ] 김대리 확인` 로 시작하는 메모는 라이브러리에서 그
이름으로 남는다. AI 메뉴의 **제목** 은 제목 줄 하나를 제안하고, 적용하면 본문 맨 위에 `# 제목`
으로 들어간다 — 라이브러리만 아는 숨은 필드가 아니라 이 앱의 표기 그대로, 사용자가 지울 수 있는
한 줄로.

미리보기는 재작성과 같은 창을 쓴다. 제안이 "본문 앞에 한 줄이 붙은 본문" 이라서, 차이 보기와
적용과 리비전과 충돌 검사가 이 동작을 몰라도 그대로 작동한다. 이미 제목으로 시작하는 메모는 그
줄이 교체된다 — 제목 두 줄은 이름이 나아진 메모가 아니라 말을 더듬는 메모다.

## 관련 메모

AI 메뉴의 **관련 메모** 는 이 메모와 비슷하게 읽히는 메모를 보여 준다. 누르면 그 메모가 바탕화면에
뜬다. **생성을 한 번도 하지 않는다** — 저장할 때 만들어 둔 벡터끼리 코사인을 재는 것이 전부라
25초가 아니라 밀리초 단위로 끝난다.

임베딩을 다시 만들지 않고 `IVectorIndex.FindSimilarAsync` 로 **저장된 벡터를 그대로** 쓴다. 색인에
이미 들어 있는 텍스트를 다시 임베딩하는 것은 왕복 한 번을 더 내는 일이고, 청크로 나뉘어 저장된 것을
한 덩어리로 임베딩하면 값도 미묘하게 달라진다.

메모 점수는 **가장 가까운 청크 한 쌍** 으로 매긴다. 평균을 쓰면 이 기능이 가장 쓸모 있는 경우가
묻힌다 — 긴 메모가 다른 메모와 한 문단을 공유하면 그 문단으로 이어진 것이고, 나머지 본문이 그
연결을 표결로 지워서는 안 된다.

유사도가 0.92를 넘으면 `거의 같음` 으로 표시한다. bge-m3 기준 무관한 한국어 산문이 0.3~0.5,
실제로 관련된 메모가 0.6~0.8에 앉으므로, "거의 같다" 는 주장은 그보다 한참 위에서만 값을 한다 —
틀린 주장은 사용자를 붙이면 안 되는 메모 둘을 합치러 보낸다.

`⋯` 메뉴가 아니라 AI 메뉴에 있는 이유는 임베딩 모델이 필요하기 때문이다. 모델이 없으면 다른 AI
타일과 같이 비활성이고, 그 이유가 메뉴 맨 아래에 적힌다.

## 노트북 자동 분류

관련 메모 창에서 유사도 0.7을 넘는 이웃이 둘 이상이면 **노트북으로 묶기** 가 나타난다. 누르면
노트북이 만들어지고 그 메모들이 들어간다.

이것이 `SetNotebookAsync` 를 호출하는 앱 안의 첫 번째 코드다. 노트북은 만들 수도 있고 걸러 볼 수도
있었지만 **아무것도 넣을 수 없는 서랍** 이었다 — 어떤 메모가 함께 가는지 아는 것이 없었기 때문이다.
벡터는 안다.

모델은 이름 짓기 한 가지만 한다. 어떤 메모가 속하는지는 임베딩이 더 잘, 그리고 밀리초 안에
답하므로, 작은 모델에게 고르는 일까지 맡기면 비싸고 불안한 쪽이 사용자의 메모를 옮기는 판단을 쥐게
된다. 이름도 본문이 아니라 제목들에서 짓는다.

셋 미만이면 제안하지 않는다. 둘은 우연이고, 셋이 같은 이야기면 주제다 — 짝마다 노트북을 만들면
사이드바가 두 개짜리 폴더로 찬다. 관련 목록에 보이는 기준(읽을 가치)보다 높은 기준을 쓰는 이유는,
이쪽은 사용자의 메모를 실제로 옮기기 때문이다.

## 메모 Q&A

`Ctrl+Space` (또는 AI 메뉴 맨 아래의 `질문`) 로 사이드카를 연다. 마지막으로 쓰던 메모가 있으면 그
메모만 근거로 답하고, 없으면 하이브리드 검색으로 관련 메모를 찾아 답한다 — 어느 쪽인지 창 위에
적혀 있다. 답은 토큰이 오는 대로 흘러나오고, 창을 닫으면 추론이 취소된다. 이 창은 메모를 고치지 않는다.

답 아래에 **근거 메모** 가 붙는다. 답이 오기 전에 먼저 뜨므로 수십 초를 기다리는 동안 무엇을
근거로 쓰는지 보이고, 누르면 그 메모가 바탕화면에 뜬다. 검색을 두 번 돌리지는 않는다 — 창이 먼저
검색해서 찾은 메모 id 를 `ScopedNoteIds` 로 넘기면 서비스는 그 메모들만 읽는다. 이 크기의 로컬
모델은 틀리며, 정확도를 올리는 것보다 **틀렸는지 확인할 수 있게 하는 편** 이 현실적이다.

## 명령 팔레트

`Ctrl+Space` 는 한 줄을 받아 이 앱이 그 줄로 할 수 있는 것을 전부 보여 준다 — 찾기, 묻기,
알림, 적어 두기. 예전에는 Q&A 창만 열었고, 그래서 이 앱의 유일한 전역 AI 키가 기능 하나의
단축키였다.

버튼은 넷이다 — 질문 · 알림 만들기 · 새 메모 · 오늘 브리핑. 앞의 셋은 입력한 줄로 무언가를 하므로
줄이 비면 꺼지고, 브리핑만 늘 켜져 있다: 그것만이 입력한 줄이 아니라 라이브러리 전체를 읽는다.

**검색은 모델을 기다리지 않는다.** 결과는 키를 칠 때마다 하이브리드 검색에서 오므로 가장 흔한
용도("그 메모 어디 갔지")가 밀리초 안에 끝난다. 모델에게는 같은 줄이 무슨 뜻인지 동시에 묻고,
답이 오면 버튼 하나를 강조할 뿐이다. 버튼은 움직이지 않는다 — 모델이 마음을 바꿀 때마다 배치가
바뀌는 팔레트는 손이 기억할 수 없다.

의도 분류에는 별도 프롬프트를 쓰지 않고 알림 파싱을 그대로 쓴다. 실제 시각으로 풀리는 줄은
알림이고 아닌 줄은 아니다 — 작은 모델에게 라벨을 고르라고 하는 것보다 날카로운 신호이고, 앱이
이미 할 줄 아는 판단이다.

## 오늘 브리핑

트레이 우클릭 또는 명령 팔레트의 **오늘 브리핑**. 오늘 울릴 알림, 아직 남은 체크박스, 최근에 고친
메모를 모아 **메모 한 장으로** 만든다.

창이 아니라 메모인 것이 요점이다. 이미 있는 검색·편집·기록·삭제가 전부 그대로 적용되고, 원치 않는
브리핑은 사람들이 이미 아는 동작으로 지워진다. 자동화가 새 표면을 만들지 않고 기존 표면 위에 앉는다.

**모은 사실이 결과물이고 모델은 문장만 다듬는다.** 모델이 없으면 사실 목록 그대로 나온다 — AI는 메모
계층의 필수 의존성이 아니라는 규칙이 여기에도 적용된다. 모델이 빈 답을 주면 목록 쪽을 남긴다.

메모를 먼저 만들어 띄우고 나서 채운다. 트레이를 눌렀는데 30초 동안 아무 일도 없으면 그것은 고장 난
메뉴로 읽힌다. 본문이 없는 메모는 브리핑에서 빠지는데, 그중 하나가 항상 이 브리핑 자신의 빈 메모다.

**정해진 시각에 자동 생성하지는 않는다.** 시작할 때 만들면 "앱 시작 = 모델 시작 금지"(보고서 p14)를
깨고, 앱이 꺼져 있던 날은 어차피 만들 수 없다. 지금은 부를 때만 만든다.

## 의미 검색 (하이브리드 검색)

Q&A가 메모를 고를 때 키워드 검색과 의미 검색을 함께 돌린다. 둘은 서로 다른 방식으로 실패한다 —
FTS는 "페이먼트 모듈 논의"라고 적힌 메모를 "결제 관련 회의"로 찾지 못하고(겹치는 단어가 없다),
임베딩은 주문번호처럼 질문 문장으로 옮기기 어려운 내용을 놓친다. 실측:

```
Q: "결제 시스템은 언제 손보기로 했어?"   (메모 본문: "페이먼트 모듈 리팩터링을 3분기에")
FTS 결과 0건 · 벡터 결과 1건 → 융합 결과 1건
```

순위 융합은 RRF(Reciprocal Rank Fusion)를 쓴다. FTS5 rank는 음수 BM25이고 벡터는 코사인이라
같은 축에서 비교할 수 없지만 순위는 비교할 수 있다. 양쪽 모두에서 나온 메모가 한쪽에서만 나온
메모를 이긴다 — 하이브리드를 쓰는 이유가 그것이다.

| 조각 | 위치 |
|---|---|
| 청킹 (빈 줄 기준, 500자, 80자 겹침) | `Core/Services/NoteChunker.cs` |
| 순위 융합 | `Core/Services/RankFusion.cs` |
| 임베딩 호출 (`/api/embed`) | `Ai/OllamaEmbeddingService.cs` |
| 벡터 저장·검색 | `Data/SqliteVectorIndex.cs` (`002_embeddings.sql`) |
| 저장 뒤 색인 | `App/Services/EmbeddingIndexer.cs` |
| 키워드+의미 결합 | `App/Services/HybridRetriever.cs` |

보고서(p8)는 sqlite-vec을 지목하면서 같은 문단에서 pre-v1이라 파괴적 변경 가능성을 경고한다.
그래서 실제로 넣은 건 **평범한 SQLite 테이블에 float32 BLOB을 넣고 코사인을 in-process로 도는
브루트포스**다. 아키텍처별 네이티브 확장을 싣고 업그레이드마다 재검증하는 비용이, 수천 개 벡터를
몇 밀리초에 훑는 이득보다 크다. `IVectorIndex` 뒤에 있으므로 그 비용이 정당해지는 날 바뀌는 파일은
`SqliteVectorIndex.cs` 하나다.

임베딩은 **저장의 결과이지 저장의 일부가 아니다**. 저장은 그대로 30ms 안에 끝나고
(보고서 p13), 벡터는 잠시 뒤 따라온다. 임베딩 모델이 없으면 아무 오류도 내지 않고 그 메모가 의미
검색에서 빠질 뿐이다. 같은 메모를 연달아 고치면 큐에서 하나로 합쳐진다.

모델 이름이 행마다 저장되므로, `ai.embeddingModel` 을 바꾸면 이전 모델의 벡터는 비교 대상에서
빠지고 "아직 색인 안 됨"으로 취급돼 다시 만들어진다. 서로 다른 모델의 벡터를 섞어 비교하는 일은
없다. 실행 중에 배경에서 25개씩 이어 받아, 색인이 없는 메모가 없어질 때까지 따라잡는다. 한 회차가
아무것도 색인하지 못하면 — 임베딩 모델이 없을 때가 그렇다 — 회차를 끝내고 다음 실행에 다시 시도한다.

bge-m3는 1024차원이고, 질문 하나를 임베딩하는 데 약 0.3초가 걸린다(모델이 올라가 있을 때).
